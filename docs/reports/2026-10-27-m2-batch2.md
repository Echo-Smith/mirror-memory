## 二、每项设计决定（及与任务书不同处）

**任务 0**：检查实现在 `tenancy.assert_tenant_table_names()`，模型 import 时运行一次。反例测试直接演示漏洞本身：把一张 `pg_` 前缀的假表挂进租户表集合后，同一形态的语句（对真表判违规）被判放行——这就是检查存在的理由。

**任务 1（RLS）**
- 角色三件套：owner（建表/迁移/DDL）、app（运行时登录，非 owner、无 BYPASSRLS、不能 ALTER）、maintenance（只给 `system_scope` 白名单调用点，独立引擎/连接池）。**maintenance 选择专门策略而非 BYPASSRLS**：策略是表级、在 `pg_policies` 逐表可见、可逐表撤销的对象，角色仍是普通登录；BYPASSRLS 会无声绕过这个库现在与将来每一张表的每一条策略。owner 受 `FORCE` 约束，同样由维护策略放行（有测试证明：删掉维护策略后 owner 读 0 行）。
- 策略：每张租户表 `ENABLE` + `FORCE ROW LEVEL SECURITY`；`mm_tenant_rows` FOR ALL TO app，USING 与 WITH CHECK 均为 `tenant_id = current_setting('mm.tenant_id', true) AND app_id = current_setting('mm.app_id', true)`——未设置时谓词为 NULL，读 0 行、写报错（fail-closed）；`mm_maintenance_rows` FOR ALL TO maintenance, owner，`(true)`。安装为迁移**第 3 版本步骤**（可重入：角色缺则建、所有权/GRANT/ENABLE/FORCE 幂等、策略 DROP IF EXISTS 后重建）。
- 租户设置：`Engine` 类级 **`begin` 事件监听器**，每个事务开始执行一条参数化、事务级 `set_config`（`is_local=true`）。与任务书的差别：没有放在 Session 层，而是连接层——实测 SQLAlchemy 2.1 对 **autobegin 也触发 `begin`**，Session 与 `engine.connect()` 两条路径同一钩子覆盖，Session commit 后继续查询自动重设；`set_config` 的清理由 PostgreSQL 自己在 COMMIT/ROLLBACK 做，池复用不可能把租户带进下一个事务。例外：AUTOCOMMIT 连接没有事务可挂设置，不得用于租户工作（策略会 fail-closed）。
- **与任务书不同的适配**（任务书未预见 RLS 对现有系统调用点的反作用）：① `worker.process_pending` 的扫描会话移到 `system_scope` 内创建；② 在 `system_scope` 内创建的 Session，若 bind 是 PG 引擎且 RLS 开启，自动重绑到注册的维护引擎（按"去口令的应用库 URL"注册，`MM_MAINTENANCE_DATABASE_URL`）；未注册是**硬错误**——否则跨租户扫描会以 app 角色运行、静默看到空队列；③ 单租户启动探针（不走 Session 的裸连接）改用 `rls.system_engine_for()`；④ 运行期姿态校验：PG 引擎启动即查 schema 在位、每表 RLS 在位、**当前登录不是超级用户 / owner / BYPASSRLS**——超级用户会无声通过所有策略，让第二道防线形同虚设。
- **测试 5 的落法**（与任务书"7 个点在 maintenance 角色下正常工作"的出入）：worker 扫描点与启动探针点走 maintenance 引擎（有测试）；5 个迁移内部点以**迁移登录（owner）**运行——它们发 DDL，需要表所有权，maintenance 角色不该有；owner 由维护策略放行（测试证明 FORCE 下 owner 全表可见）。审计器相应新增：引擎自己的 set_config 语句精确放行；其他任何设置 `mm.*` GUC、`SET/RESET ROLE`、`SET SESSION AUTHORIZATION`、`row_security` 操作一律硬违规；GRANT / CREATE|DROP POLICY / CREATE ROLE 单语句形态作为不读行的 DDL 放行（真正拦住 app 角色的是所有权——数据库报 `must be owner`）。
- harness：PG 腿每个测试在 admin 上重建 schema 并安装 RLS 姿态，`db_session` 经 **app 角色引擎**打开——整套 1249 个测试都在 RLS 之下运行，而不是只有专门的 RLS 测试。

**任务 2（连接池）**
- `core/pg_engine.build_engine` 成为所有 PG 引擎的唯一构造路径（server、宿主 MemoryEngine、维护引擎）。池参数 `MM_PG_POOL_SIZE`（默认 5）/`MM_PG_MAX_OVERFLOW`（10）/`MM_PG_POOL_PRE_PING`（开）/`MM_PG_POOL_RECYCLE`（1800 s）；三个超时经 libpq `options` **建连时**设置（零额外往返）：statement_timeout 30 s、lock_timeout 5 s、idle_in_transaction_session_timeout 60 s，默认值理由见 `docs/postgres-deployment.md`；值进入连接串前校验为非负整数，畸形值启动即拒。SQLite 引擎保持原样（不传池参数）。
- server 在 PG 上**所有租户共用一个 SQLAlchemy Engine**：lifespan 引擎的池交给每个租户的 `MemoryEngine` 包装（`engine=…, schema_ready=True`），LRU 缓存的是轻量包装，淘汰**不会** dispose 共享池；SQLite 保持每租户一引擎。
- 新租户引擎创建移出缓存锁：锁内只放 `_Pending` 占位（Future），创建在锁外；同租户并发首请求等同一个结果（含同一个异常），其他租户不被冷启动阻塞（有计时断言的测试）。创建失败会释放占位并传播异常，下次重试。

**任务 3（并发移植）**：分类表见第四节。补充两点：① 失败语义按 v1 而非 v2（表中逐条标注）；② **记录了一处 v1/v2 语义差异未改**：v1 的租约围栏只看 lease_token，过期但无人重认的租约仍归持有者（v2 会失败该 publish）——这是行为决定，留给用户。
- harness 顺带修复（测量/诊断工具缺陷）：失败测试若持有未提交事务的 Session，失败帧引用让连接不释放（`dispose` 关不掉已借出连接），下一测试的 schema 重建会在 `DROP TABLE` 上永久等锁。`_pg_fresh_schema` 现在 drop 带 2 s 事务级 `lock_timeout`，超时则终止泄漏后端、**发出点名告警**（含泄漏语句）并重试——运行继续，泄漏的失败照常报告。

**任务 4（EXPLAIN）**：见第五节。

**任务 5（性能终验）**：方法论沿用第一批补丁（同 run 交错 ×3、junit 校验），以"模式"替代"revision"：测量集 = 三模式校准跑中**全部通过**的测试 ID 交集（隔离断言类测试在 C 模式按设计失败，从三个模式中一并剔出，剔除清单按文件在 CI 摘要列出）；每轮三模式 junit 全部通过 |ids| 个测试且零失败才记 VALID。审计器全程关（M1 口径）。触发方式：推送到专用分支 `perf/m2-batch2`（workflow_dispatch 需文件在默认分支）；第一批的 m2-patch-perf push 触发已退役，避免每次推送重跑 150 分钟历史测量。

## 五、EXPLAIN 表格与索引决定

数据（本机与 CI 同构）：100 租户 × 1 万信念（100 用户/租户，**用户 ID 跨租户重复**——真实多租户命名空间，也是单列 `user_id` 索引的最坏情形）、事件 2:1、证据 1:1、链接 1:1、任务 1/用户（≈500 万行，58.6 s 装载）。逐条 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`，三种形态：C（应用谓词 + 超级用户，无 RLS）/ A（应用谓词 + RLS）/ B（仅 RLS 过滤）。工件：本机 `docs/artifacts/2026-10-27-m2-batch2-explain/explain_review_local.md`，CI `explain_review_ci.md`（job explain，run 40438195434）。

关键行（C 模式，基线索引）：

| 查询 | 计划 | 索引 | 行数/耗时 |
|---|---|---|---|
| recall 相关切片（ILIKE，ORDER BY last_evidence_at LIMIT 150） | Bitmap Index/Heap | `uq_mm_beliefs_user_key` 前缀 | 6 行 / 1.13 ms |
| recall 最近切片（LIMIT 25） | Bitmap Index/Heap + Sort | 同上 | 25 行 / 0.11 ms |
| 按 id 取信念 | Index Scan | `mm_beliefs_pkey` | 1 行 / 0.03 ms |
| 按信念取事件 | Index Scan | `ix_mm_belief_events_belief_id` | 1 行 / 0.04 ms |
| 按信念取证据（links ⋈ evidence） | Index Scan ×2 | `uq_mm_belief_evidence_link` + `mm_evidence_pkey` | 1 行 / 0.06 ms |
| 任务 claim（条件 UPDATE） | Index Scan | `mm_evolution_jobs_pkey` | 0 行 / 0.5 ms |
| **pending 任务扫描（维护角色，无租户）** | **Seq Scan → 采纳索引后 Index Scan** | `ix_mm_evolution_jobs_pending` | 丢 9000 → **丢 0**；462 → 34 页 |
| 删除路径（按用户删信念/事件） | Bitmap | 唯一约束 / `ix_*_user_id` ∧ 主键 | ≤ 5.2 ms @ 500 万行 |

要点：RLS 的 `current_setting(...)` 谓词可走索引（STABLE），**A/B/C 三种形态计划形状一致**；所有租户+用户、主键、按信念查找已由第一批的复合主键与唯一约束服务。

**索引决定**：
1. **新增** `ix_mm_evolution_jobs_pending`：`(created_at) WHERE status = 'pending'`（部分索引，只含待处理行，极小）。声明在模型上（新库 create_all 直建，SQLite 同样受益），存量 PG 库由迁移**第 4 步** `CREATE INDEX CONCURRENTLY` 补建（INVALID 残留先删再建，可重入，`MM_MIGRATION_LOCK_TIMEOUT` 生效）。
2. **不补** M1 删掉的 36 个单列租户索引、不加 beliefs/events/links 的租户前缀复合索引：计划已走复合主键/唯一约束，补了只有写放大（M1 的教训）。
3. **记录为可选未采纳**（工件含前后对比）：beliefs `(tenant, app, user_id, last_evidence_at DESC)`（最近切片 316→56 页、0.11→0.03 ms，但基线已 0.1 ms，不值 100 万行表的额外索引）；以 `(tenant, app, user_id)` **替换**各表单列 `ix_*_user_id`（若确认用户 ID 命名空间跨租户共享，这是结构性修法；当前只在按用户删除路径可测到 3–5 ms）；links/events 的 `(tenant, app, belief_id)`（单列 belief_id 已够）。

顺带修复（第一批潜在缺陷）：`_pkey_build_index` 把主键构建索引挂在 `Base.metadata` 上——PG 做过第 2 步主键换索引后，同进程再 `create_all` 会在事务内发 `CREATE UNIQUE INDEX CONCURRENTLY` 而失败。已改挂分离副本并加回归测试。

## 七、发现的隔离或性能问题

1. **（已修，第一批遗留）`_pkey_build_index` 污染模型元数据**：见第五节末。
2. **（已修，测量工具）占位符正则吞 JOIN**：审计器对 SQLAlchemy PG 外键反射语句误判「解析失败」（fail-closed 假阳性）；`%(c)s::VARCHAR LEFT OUTER JOIN pg_catalog.pg_class` 的 JOIN 被当类型词吞掉。改为白名单续接词（WITHOUT/WITH/TIME/ZONE/PRECISION/VARYING），加双向测试（同一形态打在租户表上仍是违规）。
3. **（已修，harness）泄漏会话永久卡死 schema 重建**：见第二节任务 3。
4. **（语义差异，未改行为）v1 租约围栏按 token 不按墙钟**：过期但无人重认的租约仍归持有者（v2 会失败该 publish）。是否改为"过期即失权"是行为决定，留给用户。
5. **（设计事实，已处理）`system_scope` 在 RLS 下的反作用**：跨租户扫描若继续走 app 引擎会静默看到空队列（不是报错）。已改为硬错误/维护引擎路由（第二节任务 1）；这类"RLS 让检查变空过"的形态值得在 M3/M4 新增调用点时复查。
6. **（性能）维护扫描的 Seq Scan**：唯一真实计划缺陷，已由 Step4 部分索引修复（第五节）。
