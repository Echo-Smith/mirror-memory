## 二、设计决定（与任务书不同处）+ 两层授权真值表

**授权模型**（`core/authorization.py`）：`mm_purpose_grants`（复合主键 tenant/app/user/purpose、CAS version、JSON allowed_operations、issued/expires/revoked、issuer）+ `mm_purpose_grant_events`（追加式审计：action/operation/decision/版本迁移/actor/reason）。操作词表固定 7 项（observe/recall/correct/forget/export/explain/extract），未知操作直接抛错。`grant_purpose`/`revoke_purpose` 为 consent 类认可写入者，已登记调用方白名单（含 authorization 模块自身的测试用 autogrant 路径与 api）；首签并发撞复合主键、更新走 CAS，PG 真实并发 2×50 轮每轮恰一方胜出。迁移第 6 步（LATEST_VERSION=6）：模型元数据建表、`mm_evolution_jobs.purpose`（可空→分批回填→非阻塞 NOT NULL）、RLS 计划覆盖新表。

**与任务书不同的地方**：
1. **authorize 拒绝在 system_scope 下直接抛错**（任务书只要求写明调用点引擎）：维护引擎上租户过滤缺失，他租户的授权可能满足检查——"RLS 让检查变空过"的授权版，fail-closed 优先。每个调用点的引擎列在入口清单。
2. **两层门禁的求值顺序**：purpose 层全部先于 feature 层（missing_purpose → no_grant → revoked → expired → operation_not_allowed → feature_disabled）；worker 里 consent（memory_disabled）先于授权检查——保持既有 reason 语义（有测试锁定）。
3. **无隐式默认**：`default_purpose` 是显式参数；测试通过 conftest 的 monkeypatch `setdefault` 注入 `default_purpose="test"`（引擎参数本身，不是引擎内隐式默认），purpose 门禁测试用 `default_purpose=None` 显式关闭。
4. **MM_TEST_AUTOGRANT**（测试脚手架，生产禁用）：authorize 首次 no_grant 时**真实签发**全操作授权（真实行 + 真实审计事件，issuer="test-autogrant"），避免 1200+ 测试逐个铺授权夹具；purpose 门禁测试本地关闭。并发首请求竞态下输家重读赢家授权而非拒绝。
5. **forget 路径的授权事件**落在 `mm_purpose_grant_events`（action="invoked"，operation="forget"，decision="allowed_regardless"），不改授权行本身。
6. **提交粒度**：任务 2/3 与任务 4 的机制相互缠绕（同文件、同批测试），合并为一个实现提交（6e913fa，提交信息含任务 4 机制说明）；任务 0（078fa73）、任务 1（5a3467c）、任务 5（测试表）独立可辨。

## 三、入口清单（ENTRY_REGISTRY，测试发现强制）

**库 API**（全部 tenant(app) 引擎、purpose=参数或引擎 default_purpose）：observe→observe；recall/panel→recall；get_beliefs/get_verification_candidates/belief_history/explain→explain；run_verification/correct/restore_belief→correct；run_metabolism→extract；forget_belief/forget_session/delete_memories→forget（allowed_regardless，审计）。
**HTTP server**（全部 X-MM-Purpose header、中间件对照 key 注册集合 403 先于 SQL、tenant(app) 引擎）：observe→observe；recall/panel→recall；beliefs/belief_by_id/stats→explain；delete_memories→forget（审计）。
**后台 worker**：`_process_single_job`/`process_pending`→extract；purpose 来自任务行（入队时记录触发 observe 的 purpose）；队列扫描在维护引擎（只读队列，不授权）。
**bench**：runner/longrun/statebench×2/metabolism→经引擎入口；`default_purpose="benchmark"` + 幂等 `grant_bench_purpose`。
**显式不加门控**（UNGATED_ENGINE_METHODS，有存在性测试）：set_enabled/set_consent/grant_purpose/revoke_purpose——授权管理本身。
**机制**：`ENTRY_REGISTRY` + `UNGATED_ENGINE_METHODS` 在 `core/authorization.py`；两个发现测试（引擎公开方法、server 路由）对未登记入口直接失败（与 system_scope 白名单同机制）。

**复查结论（RLS 空过形态）**：authorize() 在 system_scope 下抛 RuntimeError、无租户上下文时由租户钩子 fail-closed——不存在"维护引擎查不到记录当作 no_grant"的路径。所有调用点用 tenant(app) 引擎；worker 队列扫描不调用 authorize。

## 四、撤销并发的交错分析与测试结果

**无锁的漏洞交错**（READ COMMITTED，发布事务内 re-check 后）：`发布: SELECT grant(v1,未撤销)→决定发布` → `撤销: UPDATE...SET revoked_at; COMMIT` → `发布: Publisher 写入; COMMIT`——撤销已提交而记忆仍落地。发布事务的后续语句虽能看到撤销（每语句新快照），但决定已作出。**FOR SHARE 修复**：re-check 对授权行取共享锁，撤销 UPDATE 需互斥排他锁，阻塞至发布事务结束——两事务严格排序，"撤销已提交"与"发布已提交"不可能同时成立。SQLite 无 FOR SHARE（语法错误，不发出）；写者由 journal 的 EXCLUSIVE 串行，撤销中途提交会使发布写 BUSY 回滚——同一不变量。

**测试**（`tests/test_purpose_revocation.py`，PG 真实线程）：
- 撤销夹在 claim 与 publish 之间 ×50：每轮任务 cancelled（authorization_revoked 或快照门 revoked），种子信念之外零写入 ✅
- 撤销与发布并发（barrier 对齐）×50：每轮要么 completed 且完成时刻 ≤ 撤销提交时刻，要么 cancelled；不变量"撤销提交后无记忆落地"50/50 成立 ✅

## 七、发现的隔离或授权问题

1. **（测试缺陷，已修）`test_auth_with_valid_key` 用内存 sqlite**：pre-M3 该测试通过只是因为无 LLM 的 observe 从不触库；authorize 成为请求首条语句后暴露"内存库每线程独立"。改文件库。
2. **（产品缺陷，已修）`_resolve_tenant` 解包错误**：purpose 注册表三元组化后误把 tenant_id 字符串当 (tenant, app) 返回 → `tenant_scope("t","A")`，全部 server 测试的跨租户断言抓住。
3. **（产品缺陷，已修）worker 通用失败处理器在 PG 上不先 rollback**：授权拒绝使事务 aborted 后 bookkeeping UPDATE 报 InFailedSqlTransaction 且任务卡 pending。现在先回滚再记 bookkeeping（围栏 UPDATE 仍保护记账本身）。
4. **（harness，已修）schema 重建自愈不识别 40P01 死锁**：泄漏锁/死锁同因，一并处理。
5. **（测量口径）4 个机制测试进不了"审计器关"交集**：auditor 缓存 ×2（需监听器装着）、writer_callers ×2（读根目录 yaml，checkout 不回退）。已在验收工作流过滤，逐条列明。
6. **新增 system_scope 使用点：无**（白名单保持 7 调用点；authorize 反而拒绝在 system_scope 内运行）。
