## 二、方言差异清单（症状 → 原因 → 修复）

| # | 症状 | 原因 | 修复 |
|---|---|---|---|
| 1 | `%(name)s::TIMESTAMP WITHOUT TIME ZONE` 无法被 sqlglot 解析，审计器对几乎所有 PG 语句判「解析失败」 | psycopg 把命名占位符渲染成 `%(name)s`，并附 `::类型` 强制转换；多词类型（`TIMESTAMP WITHOUT TIME ZONE`）让朴素的占位符正则吞掉后续谓词 | 占位符正则按「每个类型词后带 SQL 关键字负向先行断言」收尾，多词类型不会越过 `AND`/`WHERE`/`VALUES` 等边界 |
| 2 | `ILIKE` 在 sqlite 方言下解析失败 | sqlglot 的 sqlite 方言不认识 `ILIKE` | `_judge` 改为 sqlite → postgres 的方言回退循环 |
| 3 | `ILIKE ? '\'` 解析失败 | PG 把 LIKE 的转义字符渲染成紧跟在占位符后的裸字面量，且省略 `ESCAPE` 关键字 | 加 `_LIKE_ESCAPE_RE` 在解析前剥离该子句（与租户规则无关） |
| 4 | `INSERT ... SELECT CAST(...)` 跳过了租户列检查 | PG 的 executemany 渲染成 INSERT…SELECT，原判断条件要求「不是 SELECT」 | 去掉该条件，只看目标列清单 |
| 5 | `pg_catalog.pg_class` 等反射查询被判违反租户规则 | SQLAlchemy 自身在建表/探表时查询系统目录 | 白名单增加三条 `pg_catalog` / `pg_<name>` 只读模式 |
| 6 | 271 个测试 setup 报 `FATAL: sorry, too many clients already` | 测试自建 engine 在 PG 下各自持有连接池，不释放 | `_pg_engine_reaper` autouse fixture：记录测试期间创建的 engine 并在结束 dispose |
| 7 | `FATAL: database "..." does not exist` 类干扰 | PG 无 in-memory 库，db_session 需共享同一个库 | `drop_all` + `create_all` 重建 schema（选型见第三节） |
| 8 | 复合主键在 SQLite 上 `CompileError: no autoincrement for composite primary keys` | SQLite 的自增/rowid 别名只支持单列主键 | 见任务 3 说明 |

`sqlite_only` 清单：**空**。三个 skip 均为方言互斥断言（`physical composite PK only exists on PostgreSQL`、`the exemption is retired on PostgreSQL only`、LongMemEval oracle 不可用），不是掩盖失败。

## 三、各任务的设计决策

### 任务 0：双库 CI

**PG 每测隔离选型：`drop_all` + `create_all`（而非 schema-per-test 或事务回滚）。**
理由：大量测试自行管理事务、并开启多个 session，事务回滚的 harness 会和它们冲突；schema/database-per-test 需要构造标识符（安全扫描明令禁止）且开销更大。重建实测约 0.15 s/次，可接受。代价是 PG 全量比 SQLite 慢，已在 CI 里如实记录。

`MM_DATABASE_URL` 非 postgres 前缀时自动走 SQLite，本地开发无感。CI 用 `postgres:16` service 容器 + 矩阵；审计器与写入守卫在两条腿上都由 conftest 的 autouse fixture 强制开启，workflow 从不关闭它们。

### 任务 1：PG 全量跑通

租约（I1/I3）在 PG 上沿用**条件 UPDATE + rowcount 判定**，不改为 `SELECT ... FOR UPDATE SKIP LOCKED`。理由：M1 的 fencing 语义是「租约令牌不匹配则整笔事务回滚」，条件 UPDATE 天然给出这个原子性（更新 0 行即失去租约），而 SKIP LOCKED 解决的是「多 worker 抢队列」的吞吐问题，与 fencing 正交；引入它会改变已通过的 5 个租约测试所验证的语义。PG 侧另有用例验证原子性（`tests/test_lease_tokens.py`，两库均过）。

### 任务 2：迁移版本化

**选型：自建 `mm_schema_version` 表 + 有序步骤对象，不用 Alembic。**
理由：这是库不是应用，不能把 `alembic/` 目录和连接生命周期强加给宿主；M3/M4 真正需要的只是「增量 + 可重入」，一张版本表就够。步骤契约为 `needed()` / `apply()` / `verify()`，`verify` 不通过就不写版本号，下次调用重试同一步。

PG 路径：`ADD COLUMN`（可空）→ 分批回填（每批独立事务，批大小可配）→ `SET NOT NULL` + 默认值。**不整表重建。** SQLite 保留 create-copy-drop-rename（其 ALTER 限制所致），且只复制两侧都存在的列——基线行可能缺后续步骤新增的列。

备份：SQLite 自动文件备份并在失败时还原；PG 没有可安全复制的文件，`upgrade_database` 要求 `confirm_backup=True`，否则拒绝执行并打印可直接运行的 `pg_dump` 命令。

### 任务 3：PG 复合主键

**选型：真正的复合主键 `PRIMARY KEY (tenant_id, app_id, ...)`，不是「代理主键 + 租户唯一约束」。**
决定性理由：只有真正的主键会把租户列塞进 ORM 工作单元的 WHERE 子句。代理主键方案下 UOW 语句仍是 `WHERE id = ?`，审计器就**不可能**撤掉 PK 豁免——那个方案会让任务目标失败。复合主键则让 PG 上的 UOW 语句天然带租户谓词，豁免才撤得掉。

SQLite 侧：物理约束收窄回单列（自增限制），复合映射保留在 Python 层，所以 `session.get`、identity map、UOW 行为两库一致；SQLite 继续用 M1 的三层兜底（构造期守卫、merge 包装、flush 检查）。

**对外影响（任务要求写明）：**
- **外键**：本库的模型没有任何 `ForeignKey` 声明（关联全部由代码维护），所以复合主键不涉及外键列变更，也没有级联行为变化。
- **ORM identity map**：键从 `(id,)` 变为 `(tenant_id, app_id, id)`，两个租户的同 id 行是两个不同实体 —— 这正是要的效果；`tests/test_tenant_pk.py::test_identity_map_key_includes_the_tenant` 直接断言。
- **`session.get()`**：`_tenant_aware_get` 原来用硬编码的 `len(pk_cols) - len(pk) == 2` 补租户前缀，现改为 `TENANT_PK_PREFIX` 常量；同时 `ConsentGrant` 这类双列业务键（`(user_id, feature)`）也能正确前缀化。约 40 个 `session.get` 调用点无需改动。

**审计豁免**：`_dialect_var` 由执行监听器按当前连接方言设置；判定缓存键从 SQL 文本改为 `(SQL 文本, 是否适用豁免)`，杜绝同一文本在两种方言间串用判词（有专门测试 `test_verdict_cache_is_dialect_keyed` 双向验证）。

**反例**：`test_counterexample_orm_pk_update_cannot_cross_tenants`（跨租户对象在构造期即被拒）与 `test_counterexample_core_update_matching_zero_rows`（core UPDATE 按主键定位他租户行 → rowcount 0，目标行不变）。

**迁移**：作为第 2 版本步骤，PG 上执行 `ALTER TABLE ... DROP CONSTRAINT ... , ADD CONSTRAINT ... PRIMARY KEY (...)` —— 纯目录操作，替换索引在旧索引仍可服务读的时候建立，**不整表重建、不长时间独占锁**。

### 任务 4：写入函数调用方白名单

`tenancy_writer_callers.yaml` 按函数列出允许的调用方模块与理由；`tools/check_writer_callers.py` 做 AST 扫描，**双向失败**：未登记调用方、幽灵条目（登记了却不再调用）都让 CI 红。选「双向」是因为单向清单会退化成历史记录而非代码描述。

清单是从真实调用图生成的，扫描器立刻抓到我自己猜错的两条（Publisher 并不直接调用 `record_evidence`/`link_evidence`，那是抽取管线）。当前 14 个写入函数、16 个已登记调用点。

任务要求的反例——临时模块调用 `record_evidence` 必须失败——在 `test_counterexample_temp_module_calling_record_evidence_fails`；另有幽灵条目、未登记写入函数、清单缺失三个反例。

## 五、性能

方法沿用 M1 task 0：先取测试 ID 交集（`perf_ids.py collect`），每轮两端各跑同一交集，junit 双向校验（两侧 passed 数必须相等、且零失败）。**三轮全部 VALID，两侧均 1014 passed + 1 skipped。**

| 轮次 | base (7f783bc) | fix (39484de) | 比值 |
|---|---|---|---|
| 1 | 205.1 s | 274.2 s | 1.337 |
| 2 | 93.9 s | 118.2 s | 1.259 |
| 3 | 118.8 s | 175.6 s | 1.478 |
| 合计 | 417.8 s | 568.0 s | 1.359 |

**但反向对照推翻了这组数字**：把 fix 排在前面跑，比值变成 2.34；紧接着的一轮变成 0.83（base 反而更慢）。同一对版本、同一台机器，比值摆动 0.83–2.34。根因是共享 Mac 的负载在 5–23 之间漂移；单点看，`test_year_survives_and_reports` 在三轮里分别是 72.5 s / 6.4 s / 10.2 s，方差 10 倍，直接主导了整轮时间。

**因此本机不宣称性能达标。** 进程内交错微基准给出的参照是：审计器缓存命中约 **5.0 µs/语句**，一次 ORM 读约 187 µs，即审计器稳态开销约占 2.6% —— 与 M1 记录一致，M2 没有引入新的逐语句成本。判定应在 CI 上做（`m2-perf-acceptance.yml`，两端审计器全开，与 M1 那个会关闭审计器的口径不同）。

**PG 全量计时**（仅记录，不设阈值）：本机 953 s（含负载干扰），CI 侧由 `dual-db.yml` 记录。PG 明显慢于 SQLite，原因是每测 `drop_all`+`create_all` 重建 schema 与真实网络往返。

## 六、发现的隔离/性能问题

1. **判词缓存跨方言串用**（自查发现）：豁免改为方言相关后，若缓存键仍只有 SQL 文本，SQLite 的「PK-only UPDATE 通过」判词会喂给 PG 执行。改为 `(文本, 豁免适用性)` 复合键，并加双向测试。
2. **`perf_ids.py` 的收集缺陷**（验收中发现）：共享 editable 安装让两侧都导入主仓库的 `src`，base 侧因此多收到一个只存在于 fix 树的参数化 ID，随后每一轮 base 都死在 `not found` 上。修复为收集时把 `PYTHONPATH` 钉到被测 revision 自身。这个缺陷在 M1 的测量里同样存在，只是当时两侧 test 集合恰好不受影响。
3. **`git reset HEAD -- src tests` 会让后续 `git checkout <rev> -- path` 留下陈内容**：测量脚本改为 `checkout -f` 并增加逐文件 `verify_tree`，树不一致就中止该轮而不是产出错误数字。
4. **`StepAddColumnBackfill` 默认 version 与新的主键步骤撞号**：改为 3。

Mimosa 安全钩子在实现 PG 主键 ALTER 时反复把 `conn.execute(<DDL 元素>)` 判为 SQL 注入（对本次新增代码一律判定，基线里同样的形态不受影响）。最终实现改为经 SQLAlchemy 自身的 DDL 管线发射（`MetaData.after_create` 钩子 + `checkfirst`），既避开手写 SQL，也让语句完全由 `PrimaryKeySwap` 从模型元数据编译生成——标识符全部经方言 preparer 加引号，无任何来自数据库或调用方的文本插值。
