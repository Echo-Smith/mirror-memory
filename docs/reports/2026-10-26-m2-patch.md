## 二、审计器白名单修复（隔离漏洞）

**漏洞**：三条前缀正则把「语句里任意位置出现 `FROM pg_catalog.` / `FROM pg_xxx` / 以 `SELECT pg_catalog.` 开头」的语句整条放行。可构造：

```sql
SELECT * FROM mm_beliefs WHERE id IN (SELECT 1 FROM pg_catalog.pg_class)
SELECT pg_catalog.version() FROM mm_beliefs
```

——租户表读取随一个 catalog 子查询/函数走私过关。

**修法**：三条正则删除；catalog 语句改为**结构化判定**——sqlglot 解析后，语句触及的全部关系（FROM / JOIN / 子查询 / UNION / CTE 体）都是 `pg_catalog` / `information_schema`（或无 schema 的 `pg_*` 系统关系）才放行；与真实表混合的语句回落到正常租户规则；解析失败仍 fail-closed。

**反例（PG 与 SQLite 双方言参数化，全部判违规）**：catalog 子查询、JOIN（catalog 在 FROM 侧）、UNION、CTE、`catalog 函数 + 租户 FROM`、裸 `pg_*` 混合，共 6 形态 ×2 方言。**放行验证**：SQLAlchemy 真实反射语句（`pg_class` JOIN `pg_attribute`、`information_schema.columns`、`SELECT pg_catalog.version()`、裸 `pg_class`）全部放行。共 25 个新审计器测试。

### 其余白名单正则逐条排查

| 正则 | 问题 | 处理 |
| --- | --- | --- |
| `select 1` | 无（全锚定） | 不变 |
| `begin/commit/rollback`（前缀 `\b`） | **多语句走私**：`BEGIN; SELECT * FROM mm_beliefs` 整条放行（psycopg 会执行多语句字符串） | 收紧为整语句匹配（可选 `WORK`/`TRANSACTION`/`TO SAVEPOINT <名>` 后即结束） |
| `savepoint/release`（前缀） | 同上 | 收紧为 `SAVEPOINT <名>` 单语句 |
| `pragma`（前缀） | 同上 | 收紧为单 pragma（名字允许 schema 前缀点号） |
| `create table/index/savepoint`（前缀） | **CTAS 走私**：`CREATE TABLE stolen AS SELECT * FROM mm_beliefs` 整表读取并落新表 | 排除 `AS SELECT`（负向断言）+ 分号拒绝；单条 DDL 仍放行 |
| `drop table` / `alter table`（前缀） | 多语句走私 | 分号拒绝（`[^;]*;?\s*$`） |
| pg_catalog 三条 | 整条放行（本任务主漏洞） | 删除，改结构化判定 |

另外修了一个测试中暴露的解析缺陷：SQLAlchemy PG 反射把 `IN` 渲染成 `= ANY (ARRAY[%(p1)s::VARCHAR, ...])`，占位符正则的 cast 尾部把 `VARCHAR]` 的 `]` 当成类型字符吞掉，导致「解析失败 fail-closed」误伤真实反射语句。改为类型词与 `[]` 数组后缀作为一个整体单元匹配。

## 三、PG 迁移去长时间排他锁

**锁级别表格（每一步）**：

| 步骤 | 语句 | 锁级别 | 持有时间 |
|---|---|---|---|
| 加租户列 | `ADD COLUMN`（可空） | `ACCESS EXCLUSIVE`（仅目录更新） | 毫秒级 |
| NOT NULL 前置 | `ADD CONSTRAINT ... CHECK (col IS NOT NULL) NOT VALID` | `ACCESS EXCLUSIVE`（仅目录，**不扫存量行**） | 毫秒级 |
| 验证 | `VALIDATE CONSTRAINT` | `SHARE UPDATE EXCLUSIVE`（**读写全程不阻塞**） | 与表大小成正比，但不阻塞任何人 |
| SET NOT NULL | `ALTER COLUMN ... SET NOT NULL` | `ACCESS EXCLUSIVE`（PG 12+ 利用已验证 CHECK **跳过全表扫描**） | 毫秒级 |
| 清理 | `DROP CONSTRAINT IF EXISTS` | `ACCESS EXCLUSIVE`（目录） | 毫秒级 |
| 建唯一索引 | `CREATE UNIQUE INDEX CONCURRENTLY`（事务外） | `SHARE UPDATE EXCLUSIVE`（等待旧快照，**不阻塞新读写**） | 与表大小成正比 |
| 换主键 | `DROP CONSTRAINT + ADD CONSTRAINT ... PRIMARY KEY USING INDEX` | `ACCESS EXCLUSIVE`（仅目录更新——索引已建好，无扫描） | 毫秒级 |

**lock_timeout**：`MM_MIGRATION_LOCK_TIMEOUT`（严格时长语法校验，默认 3s）作用于每条迁移 DDL；拿不到锁即失败（SQLSTATE 55P03），`MM_MIGRATION_LOCK_RETRIES`（默认 3，间隔 2s）重试，不再无限排队——排队的 `ACCESS EXCLUSIVE` 会阻塞其后所有读者。

**CONCURRENTLY 重入处理**：失败的 CONCURRENTLY 会留下 INVALID 索引；策略是「先删遗留再重建」——`DROP INDEX CONCURRENTLY IF EXISTS` 对 INVALID 与有效索引一视同仁，不需要按有效性分叉。

**测试**（`tests/test_pg_migration_locks.py`，`postgres_only` 标记）：
- 遗留 build 索引（普通非唯一、以及模拟 INVALID 两种来源）被删、swap 完成；
- **200k 行表转换 + 另一连接持续 SELECT**：swap 0.25–0.35s 完成，读者最大阻塞间隔 **23.5–28.8 ms**（每轮打印，供本表引用）；断言上限 2s。

## 五、SQLite 主键豁免的删除

**实验**：把豁免对全部方言关闭后跑全量——唯一失败的是「SQLite 保留豁免」这条断言本身，没有任何业务语句需要豁免。

**结论：删除。** `_is_identity_keyed`、`tenant_pk_columns`、方言门控全部移除，判词缓存键回到纯 SQL 文本（判词已与方言无关）。原理：任务 3 的复合 ORM 映射同样作用于 SQLite——UOW 的 WHERE 在 SQLite 上也带 `(tenant_id, app_id, id)`。

**保留的兜底层（与审计相互独立，全部保留）**：租户列构造期写守卫、`session.merge()` 跨租户拒绝、flush 期租户校验、读路径 `with_loader_criteria` 注入。SQLite 物理主键仍为单列——裸 PK 语句在 DB 层仍可触及他租户行，这正是审计器现在必须把它标为违规的原因。
