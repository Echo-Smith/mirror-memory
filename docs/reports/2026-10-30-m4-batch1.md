## 三、设计决定与任务书不同的地方

1. **水位表 + db_id 配对**：水位行 (db_id, applied_seq) 存主库、随备份回滚；日志条目按 db_id 键控。恢复 → 同 db_id 找回日志重放；新建库 → 新 db_id → 旧日志天然作废；日志比主库旧 → 拒绝启动。日志文件名/键即 db_id，「端侧不与主库同文件」由此保证。
2. **指纹 = hash(表名:id:created_at)**：id 复用的新行 created_at 不同、指纹不匹配、不会被误删（专项测试）。
3. **删除日志写入顺序**：日志条目在主库**提交前**写入（同一调用栈内先 append 后 commit）——日志失败 → 删除整体回滚；「日志已写、提交失败」窗口安全：重放时指纹匹配不到即为空操作、只推进水位（测试构造了提交失败并断言日志在、数据在、重放为空操作）。
4. **session 范围不升代数**：原始文本删除不改变信念状态；user/belief 范围升。
5. **快照加 source_generation（Step 11）**：读时与用户当前代数比对，不同即跳过重建——这是删除/恢复对「合成自由文本」的 AND 语义兜底（与 M3 补丁的输入出处并集互为冗余）。
6. **e2e 恢复 = DROP DATABASE + pg_restore 进全新库**（贴近真实恢复，避免 --clean 残留不确定性）；恢复后 owner 侧先补 RLS posture + Step11 grants 再 reconcile——restore 的对象自带 dump 时的授权，app 角色直接启动会拒绝。
7. 重放的 worker 侧：每个 tick 先 reconcile，ReplayPending → 跳过本 tick（保持拒绝服务），DeletionLogStale → 报错跳过；reconcile 基础设施异常 **log-and-continue**，不 wedge 清扫。
8. 本批保留期只做配置与文档（默认 35 天 ≥ 常见备份保留），未实现清理——与任务书一致（只保留，不压缩）。

## 四、写入顺序与故障窗口；重放可重入性

顺序：删除行 → （同事务）墓碑 + 代数 CAS + 水位推进 → 提交前写独立日志 → 主库 commit。两窗口：①日志失败 → 主库回滚，无未记录删除（测试）；②日志已写、提交失败 → 重放指纹匹配不到 → 空操作推进水位（测试构造 commit 失败断言日志在、数据在）。可重入性：每条条目「删指纹匹配行 + 取消任务 + 代数对齐 + 水位推进」同一事务提交，中断后从水位继续；指纹匹配使每条幂等（测试：重放两遍结果一致、第二遍 ok）。

## 五、并发与 ABA 测试结果

- 代数 CAS：8 线程 × 25 次并发 → 1..200 不重不跳（SQLite ✓；PG 腿同代码路径，PG 真实并发的 50 轮删除 vs 发布见下）。
- 删除 vs 发布 50 轮（SQLite）：每轮要么发布先完成且随后被删（信念数归零），要么任务行被删/取消；**不存在删除提交后落地的新记忆**；代数 ≥ 1。PG 50 轮见 tests/test_deletion_race_backup.py::test_deletion_vs_publish_50_rounds_sqlite 的同构实现——PG 版真实线程竞速在本地多次全绿，但 CI 共享 mm_test 的历史状态曾干扰（见第七节），最终 CI 以双库全绿 + 本测试 PG 版纳入后续批次验证。
- ABA：认领 → 恢复备份（revision 回卷到认领值）→ 重放升代数 → 发布被 cancelled(deletion_generation_changed)，零写入。
