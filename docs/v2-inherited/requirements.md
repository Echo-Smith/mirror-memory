# 需求契约

状态：Draft。架构依据见 [RFC](../../docs/plans/2026-09-16-mirror-memory-v2-architecture-rfc.md)。测试编号见 [验证指南](validation.md)。

## 使用者和边界

- 终端用户希望跨会话被准确记住，能修改、关闭和删除记忆。
- 产品开发者负责用户身份、同意与最终回复；Mirror 负责记忆处理和执行授权。
- 运行负责人需要定位失败、控制成本、恢复服务，并验证删除。
- 下一产品开发者需要通过领域适配接入，无需引入 Mirror 专有概念或用户数据。

首版不建设账户、支付、聊天前端、图平台或自主调参系统。无旧 Mirror API/数据兼容要求；新版自身仍须可升级和恢复。

## 可验收需求

| ID | 当……时，系统必须…… | 验证 |
| --- | --- | --- |
| R01 隔离 | 当调用方提供 Scope 时，只能访问可信身份允许的 tenant/app/subject；缺失、伪造、跨应用引用须拒绝，且不泄露目标是否存在。 | C01 |
| R02 授权 | 当握手缺失、授权过期或操作不在许可范围时，拒绝该操作；当撤销版本被确认后，旧版本不得提交新结果或通过后续召回复核。 | C02–C04 |
| R03 可靠接收 | 当返回 accepted 时，Evidence 与任务必须已共同提交；同事件重复发送不产生重复结果，同键不同内容返回冲突。 | C05 |
| R04 来源 | 当候选被发布时，来源必须有效且同域，角色与引用匹配；模型推测不能冒充用户陈述，无来源候选不可批准。 | C08 |
| R05 后台一致性 | 当任务重复投递、租约失效或 worker 崩溃时，允许安全恢复，不能重复强化或覆盖更新的视图。 | C06–C07 |
| R06 召回 | 当请求当前记忆时，只返回获准、当前有效且在预算内的内容；pending、empty、denied、timeout 必须可区分。历史模式不能突破当前权限。 | C09–C10 |
| R07 纠正 | 当用户明确纠正一个已识别的记忆目标时，在确认操作后停止旧版本用于当前召回；新结果可异步形成，不能悄悄恢复旧值。 | C11 |
| R08 删除 | 当 forget 阻断被确认时，所选范围不可继续使用；清理后才能标记 verified；旧任务及备份恢复不得复活已删除记忆。 | C12–C13 |
| R09 生命周期 | 当同一来源重试或被再次召回时，不增加独立证据；当模拟时间到期时按规则休眠/清理，不能把历史事实改成“未发生”。 | C14 |
| R10 可解释 | 当返回记忆时，应能查到来源链、修订、生成与授权版本、选择理由；回执默认无原文，查询回执本身也需授权。 | C15 |
| R11 用量 | 当负载和消耗达到相应门槛时，按 profile 限制、延后和恢复；并发预留、重试和在途调用计入预算，撤销/删除不被费用闸门阻断。 | C16–C17 |
| R12 升级恢复 | 当索引重建时不重新推断；当代码/schema/模型配置变更时有兼容与恢复验证；过期原文不得从旧备份重新上线。 | C13、C18 |
| R13 产品效果 | 当在产品内部试点验收时，须同时验证偏好、阶段计划、历史经历和不应记忆的情境；不能仅以用户喜欢回答或问答总分放行。 | Q01–Q08 |
| R14 接入体验 | 当首次开发者按指南接入时，应完成记住、等待、召回、纠正、解释、删除，且不依赖作者口头补充关键步骤。 | C19 |
| R15 跨产品 | 当第二产品接入时，复用通用契约并保持应用隔离；若需改变内核，必须记录原因并回归已有测试。 | C20 |

## 验收责任

实现负责人提供代码、自动化结果和失败证据；业务负责人确认样例期望及用途；运行负责人确认环境、预算和恢复能力。可由同一人兼任，但记录必须区分“我设计如此”与“已测得如此”。模型评分仅辅助，授权、删除、隔离等契约不得交由 LLM 自评判定。

没有通过 R01/R02/R08 的构建不得接入真实个人数据。R13 未通过时可继续合成数据工程验证，不得宣称试点成功。R15 未通过时只宣称已验证首个产品，不宣称通用性已得到证明。
